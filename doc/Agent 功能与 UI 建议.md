# Agent 功能与 UI 建议

承接 `doc/Agent 优化建议.md`（那一份讲代码正确性与工程问题），本文只谈**产品功能**与**界面交互**。
每条都标了依据的文件位置，方便直接落地。

---

# 一、功能面

## 1. 补上「生成 → 校验」这一环（最高价值）

现在整条链路是「描述需求 → 模型吐三件套 → 落盘运行」，中间**没有任何本地校验**。而提示词自己承认这个环境最常见的失败是「臆造方法名」，且「在本地完全看不出来，只在用户运行脚本时才炸」。

三样东西都是现成的，成本很低：

| 校验项 | 现成能力 |
| :--- | :--- |
| 语法 | `bsh.Parser` 已随模块编译进 APK（`bsh/Parser.java:320` 的 `Line()`），只解析不执行即可报语法错 |
| 回调签名 | `PluginCallback.kt:19-90` 里写了真正会被查的签名：`onMsg(Object)`、`joinGroup(String,String)`、`quitGroup(String,String)`、`shutUpGroup(String,String,long,String)`、`onPaiYiPai(String,int,String)`、`chatInterface(int,String,String)`、`getMsg(String)->String`、`unLoadPlugin()`、菜单回调必须是 3 参或 4 参 |
| 方法名白名单 | `PluginMethod` 的 64 个公开方法，反射一次就有完整集合 |

一次签名不匹配就是「脚本加载成功但回调永远不触发」——用户最难自己排查的一类问题，而本地一条 diff 就能拦住。

**建议**：落盘前跑一遍，把结果做成两档——语法错误直接拦下并回灌给模型要求重写；签名/方法名可疑则在确认卡上标黄，让用户决定。

## 2. 补上「运行 → 报错 → 修复」这一环（次高价值）

脚本运行期异常由 `PluginError` 追加写入 **`<脚本目录>/error.txt`**（`PluginError.kt:28,52`）。也就是说这份日志**就在 `read_file` 的允许范围内**，模型拿到它几乎零成本。

**建议**：
- 新增一个 `read_script_log` 工具（读 `error.txt` 尾部若干行），或在 `prompt_task.md` 里直接告知「脚本目录下可能有 error.txt」；
- 对话里给一个「解释这次报错」按钮，把最近一次报错 + 当前代码一起送去分析；
- 提示词补一条：「报错栈里的行号对应 main.java，请只改相关部分」。

这一步做完，Agent 才从「一次性生成器」变成「可自愈的开发助手」。

## 3. 覆盖前留快照，支持回滚

覆盖确认卡上写着「原内容不可撤销。想保留原版，请先取消，再用「保存为脚本」另存新脚本」（`AgentPage.kt:1672`）。这是把风险完整地推给用户。

**建议**：覆盖前把旧目录复制一份到 `data/plugin/.backup/<id>/<时间戳>/`，覆盖后给一个「回滚到上一版」。目录通常只有几 KB～几十 KB，成本可忽略。

## 4. 让模型看得见「别的脚本」

现在只有从本地脚本卡片点「修改」时，才会把那一份脚本作为上下文带进去（`PluginViewModel.kt:360-366`）。用户说「照上次那个抽奖的写法来一个」时，模型手上什么都没有。

**建议**：加 `list_scripts()` / `read_script(id)` 两个工具（只读、限定在 plugin 目录内），或在输入框支持 `@脚本名` 引用。这同时也是「参考现有写法」这条最高效的教学路径。

## 5. 接上在线脚本库，顺手救活一段死代码

`ScriptService.fetchScriptList()` 与 `downloadAndInstall()`（在线脚本库的列表与下载安装）**在整仓库里没有任何调用方**——README 却已经把「从在线脚本库下载」写成了卖点。

**建议**：把 Agent 与在线库接上，形成一个完整闭环——在线库下载 → 以它为基线改 → 覆盖或另存；生成满意后也能导出/投稿。这比新增功能更划算：能力已经写好了，只差入口。

## 6. 会话里显式表达「基线」

- 编辑态目前只在顶栏标题上体现（`PluginScreen.kt:164`），新建会话没有基线概念；
- 更实质的问题是：`buildExistingScriptContext`（`PluginViewModel.kt:917-940`）只发 `main.java` + 附加文件，**不发 info.prop**。模型因此不知道当前脚本的 id / 版本 / 作者，它写回的新 info.prop 很可能换个 id——而「是否还在改同一份」正是靠 `pluginId == editId` 判断的（`:360`），一次即断。

**建议**：上下文里带上 info.prop 的 id 与名称（不必带全文）；界面上把「本次基线」做成一条可见的状态（例如输入框上方一行「正在改：xxx v1.2」），而不是只体现在标题。

## 7. 长脚本模式：把参数下沉到本次生成

`maxTokens` 现在是设置页里的全局值（`AgentPage.kt:1482-1488`），但「今天这个需求比较大」是临时性的。**建议**输入框旁加一个「长脚本」开关，仅对本次会话生效，省掉「去设置改 → 生成 → 改回来」。

## 8. 问答 → 任务的无缝衔接

`prompt_qa.md` 当前的做法是：拒绝产出三件套，并「提示用户切到任务模式」。但真实节奏往往是「先问一句怎么发图，接着就想让写一个」。**建议**：在问答回答下方给一个「据此生成脚本」按钮，把这一轮问答作为上下文直接切进 TASK，而不是把动作丢给用户。

## 9. 把脚本 API 文档暴露给用户

`api.md` 已经打进 APK（`AgentPrompts.readAsset`），但用户看不到。**建议**加一个可搜索的只读文档页，与 `search_api` 共用同一份检索。用户能自己核对签名，才敢相信 Agent 写的东西——这也是 `search_api` 这个工具被信任的前提。

## 10. 导出与分享

目前只有代码抽屉里对**单个文件**的复制（`AgentPage.kt:387`）。**建议**：导出脚本包（zip）、一键复制全部文件、分享会话（含代码）。

# 二、UI 面

## 1. 文件该拆了

`AgentPage.kt` 现在 1843 行、30 个私有 composable，单函数最长约 350 行。改动任何一处都要在近两千行里翻。**建议**按职责拆成四个文件（纯移动，不改行为）：对话流（气泡 / 思考区 / 工具卡）、代码抽屉、弹窗组（保存 / 覆盖 / 历史 / 设置）、输入区与欢迎页。

## 2. Emoji 当图标

顶栏 `➕ 📜 ⚙️ ✕`（`PluginScreen.kt:194-198`）、气泡 `🤖 👤`、按钮 `💾 📄 ✏️ 📋`、阶段 `🔌 💭 ✍️ 🧩 ✅ ⚠️ 🔧`（`AgentStage.kt`）、能力摘要 `🧠`。

问题有两个：Emoji 在不同 ROM / 字体下宽度与基线都不一致（工具卡靠 `Spacer(width = 8.dp)` 硬对齐，最容易歪），以及模块本来就有 `R.drawable` 图标体系（`ic_add_circle`、`ic_settings_gear`），两套风格混在一起。**建议**顶栏与主要按钮先换成矢量图标。

## 3. 「执行过程」卡片：信息密度过高

一行里塞了勾选圈、阶段图标、标题、detail、耗时五段，其中 detail 被 `weight(1f)` 压到只剩一行还带省略号，耗时字号 10sp（`AgentPage.kt:868-905`）。

**建议**：默认两行——「阶段 · 耗时」一行，工具调用单独一行（`read_file(core/base.java)` 这种形态）；detail 支持点击展开。另外这张卡在气泡**之外**、带 12dp 圆角和边框（`AgentPage.kt:838-844`），视觉重量和气泡几乎一样，容易抢焦点，可以降为无边框的浅色条。

## 4. 工具调用只给结果，不告诉用户「它读了什么」

`AgentEvent.ToolCall` 是带 `arguments` 的，但界面只显示 `ToolResult` 的 240 字预览（`AgentPipeline.kt:199` 截断），且没有展开入口。用户想知道「它到底看了哪个文件」时无从确认。

**建议**：detail 显示调用形态（`search_api(群管理)`、`read_file(core/base.java)`），点击可看完整返回。

## 5. 生成中不能排队下一条消息

`isGenerating` 时发送按钮被替换成取消按钮（`AgentPage.kt:1075-1105`），`sendAgentMessage` 也直接早退（`PluginViewModel.kt:345`）。也就是说生成中用户既不能追问、也不能排队补充信息。**建议**：允许输入并在结束时提示「已排队 / 点击发送」；或提供「停止并发送」。

## 6. 生成中的状态胶囊会盖住内容

胶囊用 `Modifier.align(Alignment.TopCenter)` 浮在消息列表上层（`AgentPage.kt:185-213`），列表自动滚到底时正好压住最新一行。**建议**：移到输入框上方（离操作更近，也不遮内容），或给列表加等高的顶部位移。

## 7. 代码抽屉：搜索与键盘

`AgentCodeViewer`（`AgentPage.kt:546-591`）只有滚动，没有搜索、没有行号跳转；几百行的 main.java 只能手翻。另外 `imePadding()` 挂在整个页面 Column 上（`:161`），抽屉又是 74% 高，编辑态弹键盘时容易把抽屉顶飞。**建议**：加关键字搜索与行跳转（`CodeHighlighter` 已有），抽屉内部单独处理 IME。

## 8. 保存对话框：默认值应该填进去，而不是只放在 hint

`name` 初始值是空串，默认名只在 hint 里（`AgentPage.kt:1529,1559`）。用户不填也能通过，结果是本地攒出一堆「Agent脚本」。**建议**把模型给的 `pluginName` 直接预填进输入框（可改）。

## 9. 覆盖确认卡缺「对比查看」

`AgentDiffSummary` 只给行数增减和方法名增删（`AgentPage.kt:1694-1760`）。想真正核对改动，用户只能取消、再点「查看代码」。**建议**在覆盖卡上直接放一个「对比查看」，抽屉里对 main.java 做上下对照。

## 10. 历史记录看不出「落盘了没有」

`AgentHistoryRow`（`AgentPage.kt:1229-1278`）显示模式、时间、条数、产物名，但没有「是否已保存」标记，也没有从历史直接回到该脚本「继续修改」的入口。**建议**：已落盘的会话加标记 + 一个「继续修改此脚本」的动作。

## 11. 欢迎页只有一个固定入口

`WelcomeView`（`AgentPage.kt:913-964`）只列出 VM 里硬编码的 6 条引导问题（`PluginViewModel.kt:214-221`）——之前删掉「选择已有脚本」的理由是「脚本卡片上已经有修改入口」，但**新建会话的第一步恰恰最需要它**。**建议**补一个「继续上次的需求」+「从某个本地脚本开始」的分区。

## 12. 设置页：base url 是最大的门槛

hint 只给 `https://api.openai.com/v1/chat/completions`（`AgentPage.kt:1362`），用户得自己知道各家兼容端点的地址形状。**建议**加一组预设（OpenAI / DeepSeek / Azure / 自定义），自动填地址与鉴权方式——Azure 那条同时能修掉上一份文档里的 P0-6（测试连接与取模型走错了鉴权头）。

## 13. 细节

- 阶段摘要那条 `10.sp` 与清单里的 `10.sp`（`:901,1808`）低于常规可读下限，建议统一到 11sp；
- 流式光标 `▌`、勾选 `✓ / ○`、清单 `● / ○` 都是纯文本符号，读屏无语义；
- 右上角三个 Emoji 按钮（`➕ 📜 ⚙️`）没有 tooltip/标签，新用户不一定猜得到「📜 是历史」。
